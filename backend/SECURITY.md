# Local single-user security

TrustVault is a local development demo for one user. It is not production-secure and does not provide multi-user isolation. Keep both development servers bound to loopback.

## Local configuration

Run `npm run setup-auth` from `backend/` to create a private `.env` with a scrypt password verifier and session/token keys. Run `npm run setup-message-key` to add a separate random 32-byte message-encryption key to an existing owner-only `.env`. Both commands refuse unsafe overwrites. The backend validates configured keys and fails closed when required configuration or the encrypted message store is unavailable. Environment variables override `.env` values.

Keep `.env` protected (mode `0600`) and backed up through a secure local process. Losing `MESSAGE_ENCRYPTION_KEY` makes the encrypted messages unreadable. Never commit `.env`, OAuth credentials, tokens, backups, or message-store files. The repository ignore rules exclude these items, but there is no Git repository in this workspace and ignore rules are not a substitute for checking files before any future commit.

## Login, sessions, and CSRF

The password is stored as a scrypt verifier. The API stores opaque session IDs in memory, uses an HttpOnly, SameSite=Strict, host-only cookie, rotates sessions on login/logout, and expires sessions after eight hours. Restarting the backend revokes sessions. The cookie uses `Secure` when HTTPS is configured; local HTTP development cannot use that flag.

State-changing requests require an allowed local Origin and a session-bound CSRF token in `X-CSRF-Token`. Authenticated API responses use `Cache-Control: no-store`. Login failures are throttled in process memory by client address and concurrent password checks; a backend restart clears the counters. This is a basic local safeguard, not distributed or durable rate limiting.

These controls do not provide multiple user accounts, account recovery, password reset, persistent sessions, or a hardened public deployment. Do not expose the development backend to a LAN or the internet.

## Encrypted message storage

The active store is `data/messages.encrypted.json`, an AES-256-GCM envelope with versioned metadata, a fresh nonce, and authenticated format metadata. The dedicated `MESSAGE_ENCRYPTION_KEY` is separate from session and token keys. Authentication and decryption are checked before the backend listens; a wrong key or tampered ciphertext prevents startup rather than falling back to plaintext.

The original `data/messages.json` was retained byte-for-byte as a plaintext rollback source and its permissions were tightened to owner-only after migration checks succeeded. A verified plaintext backup and manifest were created outside the project under the user's home directory. The migration utility verifies source and backup hashes, JSON, record count and IDs, then decrypts and compares the encrypted output before allowing the app to use it. The backup remains sensitive plaintext; protect it and do not place it in cloud-synced or shared storage. Recovery restores only to a new path and refuses to overwrite existing files.

For recovery, stop the backend first. Keep the original and verified backup untouched. Correct or restore the private `.env` key from a trusted backup, then verify the encrypted store by starting the backend. If the encrypted file is missing, rerun `npm run migrate-message-store` only after confirming the original plaintext file is present and the destination does not exist; the utility creates a new verified external backup and refuses to overwrite an existing encrypted destination. Do not delete either plaintext copy as part of this demo.

## Gmail OAuth foundation

The optional local OAuth flow uses Google's `googleapis` Node.js library and the authorization-code flow. It is disabled unless `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, and the dedicated 32-byte `TOKEN_ENCRYPTION_KEY` are configured in the project-root `.env`. The only requested and accepted scope is `https://www.googleapis.com/auth/gmail.readonly`; any missing or additional granted scope is rejected. The redirect URI is fixed to `http://localhost:4000/api/auth/google/callback`, and the local frontend origin is `http://localhost:5173`.

The start route is protected by local authentication and CSRF checks. It creates unpredictable, one-use state bound to the authenticated session in backend memory. A short-lived, callback-path-only, HttpOnly `SameSite=Lax` cookie carries a separate random flow proof so the callback works with Google's top-level GET while the existing TrustVault session cookie stays `SameSite=Strict`. The callback validates both proofs and confirms that the original session remains authenticated. OAuth errors use generic local UI messages; credentials and returned tokens are not logged, returned to the frontend, or exposed in URLs. On success, an allow-listed token bundle (access token, optional refresh token, expiry, and exact granted scope) is serialized once and encrypted with the existing AES-256-GCM token helper, then atomically written to `data/private/gmail-tokens.enc`. The directory and file are restricted to the local owner. Reads fail closed on corrupt ciphertext, invalid JSON/schema, unexpected scopes, or unsafe permissions. Authenticated status, sync, and disconnect responses use `Cache-Control: no-store`. The CSRF-protected disconnect endpoint deletes the local encrypted bundle only and does not revoke Google authorization.

The Gmail sync endpoint is authenticated and passes through the existing Origin/CSRF middleware. It verifies that the decrypted bundle's scope is exactly Gmail read-only before creating the API client. It calls `users.messages.list` with `maxResults: 5` and a partial-response field mask for IDs, then calls `users.messages.get` for no more than those five IDs using `format: metadata`, the partial-response fields `id,payload/headers(name,value)`, and exactly the `From`, `Subject`, and `Date` metadata headers. It never requests body, snippet, attachment, or broader-scope data. The response contains only `{ id, sender, subject, date }` entries and uses `Cache-Control: no-store`. A process-local limiter permits five sync attempts per client address per minute. OAuth client token-refresh events are merged with the existing bundle and saved through the encrypted token store before a preview response is returned; a persistence failure fails the request closed. Provider errors are converted to generic messages with no token values.

The UI calls these results a Gmail metadata preview and keeps them in separate transient frontend state. They are not written into the fictional/imported message store or passed to scam analysis. This feature is manual and foreground-only; metadata is not persisted or synchronized in the background. Expired/revoked authorization requires reconnecting. The app does not remotely revoke Google's grant. Losing `TOKEN_ENCRYPTION_KEY` makes the local token bundle unreadable. Before real mailbox use beyond local experiments, the project still needs reviewed key backup/recovery, durable rate limiting, dependency and deployment review, and a threat model appropriate to the intended deployment. The current local controls are not a claim of production security.

## User-triggered Gmail scam analysis

The metadata preview itself never runs scam analysis: sender, subject, and date are insufficient for a reliable assessment. A user must select one of the current five preview items, review a confirmation disclosure, and explicitly choose **Analyze selected email**. The new `POST /api/auth/google/analyze` route is behind the same authenticated-session and Origin/CSRF middleware as the other protected API routes. It re-reads the token bundle, requires exactly the Gmail read-only scope, rate-limits analysis to three requests per client address per minute in process memory, and uses `Cache-Control: no-store` from the `/api` middleware.

The handler first lists at most five recent message IDs and rejects a selected ID not present in that list. It reads only the selected message's `From`, `Subject`, `Date`, and `Content-Disposition` headers in metadata format. It next inspects that message's MIME structure with a partial-response mask that excludes body data, snippets, raw content, and attachment data. It refuses multipart messages, HTML, non-plain-text MIME types, filenames, attachment IDs, attachment dispositions, malformed structures, and bodies larger than 64 KB. Only after that gate passes does it request the selected message's top-level `text/plain` body. The body request does not include message headers, nested MIME parts, snippets, or raw content, and the backend never calls `users.messages.attachments.get`. The response is decoded with strict base64url/UTF-8 and byte limits. Empty, malformed, unsupported, or oversized messages fail closed without returning message text.

The selected text is passed only to the existing local heuristic analyzer. Raw message text, body data, snippet, HTML, and token values are not returned to the browser or logged by this handler. The API returns the selected message's sender, subject, date, and a projected assessment (score, risk level, indicators, explanation, uncertainty, safe recommendations); no message content or result is written to the vault. Frontend state is temporary and is cleared on logout, local Gmail disconnect, or leaving the Gmail view. No external AI service is used. There is no save-to-vault action in this milestone.

The gate intentionally supports only simple single-part plain-text emails; many normal multipart emails will be rejected. Gmail provider behavior has not been verified against a live mailbox in automated tests; tests use mocked API responses and assert the requested fields and formats. The feature still relies on local, process-memory rate limits and a single local user. A field mask and strict MIME checks reduce data retrieval, but this demo should not be described as production-secure or as a general-purpose safe email parser. Gmail's OAuth permission remains `gmail.readonly`; this milestone does not add or change scopes.
